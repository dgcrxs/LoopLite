# Looped Transformer 与 mHC 机制解析

## 一、为什么要有循环架构

大模型能力提升，过去只有一条路：**堆参数**。但参数量的边际收益在递减，
而显存和算力的成本是线性的。

循环架构换了个思路：**参数规模不变，增加计算深度**。

```
普通 32 层模型：  输入 → L0 → L1 → ... → L31 → 输出      （32 次层计算）
循环模型（N=2）： 输入 → L0..L3 → [L4..L27] ×2 → L28..L31 → 输出   （56 次层计算）
                                  ↑ 同一组权重跑两遍
```

代价是算力（56 次 vs 32 次），收益是显存（只存 32 层的权重）。

## 二、基座结构（以 SenseNova-Loop-9B-Preview 为准）

| 段 | 层索引 | 层数 | 权重 | 作用 |
| :-- | :-- | :-- | :-- | :-- |
| Pre-loop（A） | 0–3 | 4 | 独立 | 入口编码，把 token 变成稳定的特征 |
| Looped（B） | 4–27 | 24 | **共享** | 核心推理，跑 N 遍（默认 2） |
| Post-loop（C） | 28–31 | 4 | 独立 | 出口解码，把特征映射回词表 |

- **存储参数**：9.656B（实测，871 个张量逐张量累加）
  - 文本主干 7.94B（含 embed_tokens 1.017B）
  - lm_head 1.017B（与 embed 不共享）
  - 视觉塔 0.456B · MTP 头 0.244B
- **推理计算**：约 14.6B（56 次层计算折算的前向口径）
- **注意力**：混合式，每 4 层里 3 层线性注意力 + 1 层全注意力
- **上下文**：训练最长 262,144 tokens
- **模态**：⚠️ 这是**图文多模态**模型（含视觉塔与视频预处理），不是纯文本 LLM

> 只看 9.6B 就去估响应时间，会低估近一倍。
>

## 三、mHC：为什么循环会「跑坏」

把同一组权重跑多遍，有个致命问题：**残差流会互相污染**。

普通残差：`x_{l+1} = x_l + F(x_l)`。
循环时，`x` 反复经过同一个 `F`，信号会沿两个方向失控：
- **爆炸**：每遍都往同一个方向加，范数指数增长
- **消失**：每遍都往反方向抵消，信息被稀释

更麻烦的是「多流」情况：如果有两条残差流，跑几遍之后它们会趋同，
携带的信息变得冗余——等于白白多算了一遍。

### mHC 的解法

**Manifold-Constrained Hyper-Connections**：把残差扩展成双流，
用一个**双随机矩阵**（行和 = 列和 = 1）来做流间信息交换。

```
    x⁽¹⁾                    x⁽²⁾
      │                       │
      └──────►  [ a   1-a ] ◄─┘     双随机混合矩阵
                [ 1-a  a  ]
      │                       │
    x⁽¹⁾'                   x⁽²⁾'
```

双随机的性质保证了：
1. **守恒**：混合前后总量不变 → 不会爆炸也不会消失
2. **可逆**：双随机矩阵是 Birkhoff 多面体上的点，信息不会坍缩到低维
3. **受控**：混合强度由 Sinkhorn 归一化严格约束在流形上

### 官方 config 里的 mHC 实测值

```json
"mhc": {
  "streams": 2,           // 双流，与上面推导一致
  "iterations": 20,       // Sinkhorn 迭代 20 次（不是 5 次，精度要求高）
  "start": 4, "end": 28,  // 作用区间与循环块完全重合
  "fixed_identity": false,// 混合矩阵可学习，不是写死的恒等
  "pre_scale": 1.0
}
```

注意 `iterations: 20` 这个数——Sinkhorn 迭代次数直接决定「双随机约束」被满足得有多严。
自己实现时若图快只迭代 5 次，矩阵会偏离双随机流形，循环跑几遍就开始漂。
`src/core/loop_transformer.py` 的 `MHCMixer` 默认值与官方对齐在 20。

官方消融数据（mHC 带来的提升）：

| 评测 | w/o mHC | w/ mHC | 提升 |
| :-- | :-- | :-- | :-- |
| GPQA Diamond | 32.22 | 36.64 | **+4.42** |
| TeamBench | — | — | **+13.34** |
| BIRD-Dev | — | — | +2.36 |

TeamBench（多步 Agent 任务）+13.34 是最值得注意的：
**循环深度对多步推理的增益最大**，这正好对上我们的 Agent 场景。

## 四、我们的实现在哪里

`src/core/loop_transformer.py`：

| 组件 | 类 | 说明 |
| :-- | :-- | :-- |
| 双随机归一化 | `sinkhorn_normalize()` | Sinkhorn 迭代，对齐官方 20 次 |
| 双流混合 | `MHCMixer` | 静态参数 + 动态路由，残差式混合 |
| 循环块 | `LoopedBlock` | 24 层共享权重跑 N 遍，遍间做 mHC |
| 退出路由 | `ExitRouter` | 自适应提前退出（坍缩风险源） |
| 线性注意力 | `LinearAttention` | elu+1 特征映射，O(T) 复杂度（简化版） |
| 全注意力 | `FullAttention` | GQA，16 头 / 4 KV 头 |

> ⚠️ **简化实现 vs 官方实现的差异**（改代码前必读）：
> 官方 `qwen3_5_text` 主干用的是 **带短卷积的门控线性注意力**
> （`linear_conv_kernel_dim=4`、key 16 头 / value 32 头、head_dim 128），
> 不是这里 elu+1 的朴素线性注意力。本实现的价值在于**把循环与 mHC 的
> 数据流讲清楚**，便于做消融和稠密转循环；不要在它上面追求与官方逐位对齐。
> 要做等价替换，得照 `modeling_sensenova_loop.py` 里的线性注意力重写。

> 注意：这是**我们自己维护的实现**，用于理解、消融实验和 dense→loop 转换。
> 基座 9B 的推理走官方 `trust_remote_code=True` 的实现，不经过这里。

## 五、稠密转循环（Dense-to-Loop）

详见 `src/core/dense_to_loop.py`。三条经验：

1. **B 段取中后段，别取前段**。浅层负责「看懂 token」，重复跑收益低；
   中后段负责「推理」，重复跑收益高。
2. **B 段初始化用加权平均**，不要直接复制某一层。
   直接复制会把该层的偏置放大 N 倍。
3. **训练与推理的 loop_pass 必须一致**。训 2 遍、推 1 遍 = 分布偏移。

## 六、三个必须记住的数字

```
存储层数   = 32
前向计算   = 4 + 24N + 4     （N=2 时为 56）
参数压缩比 = 前向计算 / 存储层数 ≈ 1.75x（N=2）
```
